# Mock the Stripe API in CI

A working Stripe simulation, deployed on every push to main by a GitHub Action,
with a test suite pointed at it. Companion repo to the article of the same name
on [mockzilla.org](https://mockzilla.org/en/articles/mock-stripe-api-in-ci/).

## The point of it

Stripe publishes 419 paths in a 6.1 MB OpenAPI document. Loading all of it
costs around 881 MB of memory and most of a second before the first request is
answered, which does not fit in a simulation sized for a small plan.

`services/stripe/codegen.yml` names the six paths this test suite calls.
Filtering against it brings the spec to 1.19 MB and twelve routes, which starts
in about 120 ms:

```bash
make spec
```

That trims each service's published document against its filter and writes
`services/<name>/openapi.yml`. The
result is never committed: CI rebuilds it on every run, so the simulation
always reflects what the provider publishes today.

## Layout

```
services/stripe/codegen.yml    the endpoint filter, the file worth copying
services/stripe/config.yml     latency and error injection, to uncomment
services/stripe/openapi.yml    generated by `make spec`, gitignored
test/stripe.test.mjs           assertions against the live simulation
```

Adding a second API means a second folder with its own `codegen.yml`, and a
second `simplify` line in the Makefile pointing at that provider's spec.

## Run it locally

```bash
make spec
make serve
STRIPE_BASE_URL=http://localhost:2200/stripe make test
```

## Run it in CI

`.github/workflows/mockzilla.yml` trims the spec, publishes on every push to
main, and runs the same tests against the deployed simulation. The `GITHUB_TOKEN` is what proves
the repository is yours, so there is no key to configure.

The simulation comes up at `https://api.mockz.io/gh/<org>/<repo>`, with these
endpoints under `/stripe`.

The workflow curls one endpoint before running the tests. A freshly deployed
simulation reports itself active before it is warm, and the request that builds
the route registry can time out at the gateway.

## What this is not

It is a simulation, not Stripe. Responses are generated from the spec, so they
have the right shape and status codes without being real data, and there is no
state between calls: a customer you create is not there when you read it back.
Tests that depend on that belong against Stripe's own sandbox, on a schedule.
